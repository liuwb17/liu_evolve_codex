# v3：LLM 冷启动与多样性演化协议

目的：不输入任何人类参赛解法或既有 MOSAIC 求解器，由 LLM 生成完整初代，再由 LLM 修改源码，争取超过 kusano 既有本机实测均分 989.413157M。是否达成以最终测试为准，不能预先承诺。

## 从零的范围

API 请求是新建的独立对话，仅包含问题定义、I/O 与资源约束，以及本次 v3 运行自身生成的谱系和公开训练反馈。初代没有代码模板、人工算法骨架或指定算法方向。控制器、编译器、计时器、合法性检查与选择规则属于人工基础设施，不是 LLM 发明。LLM 的预训练记忆无法排除，因此不声称模型从未见过本题。

不得把 `data/human_references`、v1/v2 求解器或私有输入加入提示词、候选初代或 donor。候选容器仅挂载其自身编译目录与无算法的计时脚本，不挂载旧版框架库、参考代码或评测数据。API 密钥不进入候选环境。源码的新增、修复和优化均由模型响应产生；若未来人工改算法，必须另行标注，不能沿用纯 LLM 来源。

## 数据与预算

使用原始 Rust 生成器产生的官方 50 个 public inputs，按编号 `index % 5 == 4` 留出 10 例用于最终选型，其余 40 例用于演化。训练集按点数排序，均匀抽取 12 例进行初筛，其中 6 例先做编译/合法性烟雾测试。

初筛搜索预算 0.6 秒，候选进程硬上限 0.75 秒；全预算搜索 4.8 秒，候选进程硬上限 4.95 秒，低于题目 5 秒。Docker 生命周期外层独立限时 30 秒。每候选 1 CPU、512 MiB，最多 6 例并发。任何超时/非法输出计零，不剔除。最终与 kusano 比较时说明其内置 4.8 秒、进程 5 秒上限和本协议的 4.95 秒上限差异。

首轮 DeepSeek `deepseek-flash` 最多 64 次请求，每次最多 16384 输出 tokens。失败和修复占用预算，中断未知用量不视为免费。不会无界增加模型请求；增加预算须明确披露。所有请求与响应（不含密钥）存档。

执行调整：Flash 使用 6 次请求后停止（完整记录保留），改用同服务 `deepseek-v4-pro` 独立冷启动，最多 58 次请求，两者合计仍不超过 64 次。两个运行不共享候选。Pro 运行目录为 `runs/v3_pro_fromscratch`，启动参数为 `--model deepseek-v4-pro --run-dir runs/v3_pro_fromscratch --calls 58`。修复反馈增加一个实际失败的公开训练输入/输出，帮助模型复现错误；未增加人工解法。

Pro 非推理模式的早期程序仍有合法性/质量问题，因此保留候选继续运行，并启用 `--thinking enabled --max-tokens 32768`。请求总数上限不变；配置切换写入 state 的 `generation_config_changes`，每份请求亦记录实际配置。切换时未完成的保留请求按 `interrupted_usage_unknown` 计数，不假定其无费用。此次调整不提供任何已有解法或算法骨架。

接口参数依据 [DeepSeek 官方推理模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)。启用时默认推理强度为 high，temperature 被服务忽略；推理和最终输出共同消耗输出预算。第一次启用推理的修复请求用时约 277 秒，因此完整实验可能需要数小时，不能把 API 等待时间隐去。

后续一个 high 独立设计请求用尽 32768 输出 tokens，全部为推理，最终内容为空（finish_reason=length），按失败计入。随后切换 `--effort low`，其后的一个进行中请求被中止、用量未知且保留预算占用；不抹去这些成本。控制器增加 `STOP_AFTER_CURRENT` 文件检查，使后续配置调整可在一次请求及其评测完成后安全停止，避免再中断在途请求。

公开训练诊断发现早期有效初代只运行约 0.02–0.19 秒，未利用 4.8 秒预算。因此在当前请求完成后安全重载控制器，增加实际平均耗时、实例点数及两个最差公开训练实例的输入/候选输出。该反馈完全来自本次模型程序和公开训练数据，不含参考答案、人类程序或人工算法修改。源代码仍仅由后续 API 响应产生。

Pro 共保留 11 个请求名额后完成初代采样阶段，最佳公开训练均分 848.185315M。最后一个 low 请求亦用尽 32K token 而没有最终代码。安全停止后，将后续输出上限设为 65536，保持 low 推理强度和总请求上限（Flash 6 + Pro 最多 58）不变，进入现有候选的反馈演化。更多 token 上限不等于实际消耗；实际已知用量与未知中断请求分别记录，不按请求次数冒充费用。

## 演化策略

1. 先尝试 8 个无父代的独立完整设计；不把先前初代源码提供给后续冷启动请求。
2. 模型产生完整 C++17 程序。编译或运行失败最多接一次针对性修复，保留失败源码与诊断。
3. 6 例快速合法性检查 → 12 例短预算比较 → 12 例全预算筛选 → 40 例全预算评测。初代和结构创新不因短跑落后而直接淘汰；每 7 次请求也提供一次慢启动算法晋级机会。
4. 全预算目标为 `0.9 × 均分 + 0.1 × 最低四分位均分`。保留总体前三、四种点数区间各自的专家，以及不同模型描述算法族的代表。算法族描述本身并不保证真实结构不同；按实例表现保留专家是独立的多样性依据。
5. 父代 55% 选总体最佳，45% 从档案抽样。交叉 donor 按其相对父代的逐例正向增益选择。交替尝试局部改进、结构重写、计算瓶颈优化、互补组合、低分鲁棒性和新设计。
6. 只回传公开训练集的逐例反馈和近期实验摘要。不将最终验证集分数用于后续演化。
7. 明确 finalize 后，训练稳健目标前三加训练均分最佳（重复时补第四）在 10 个公开验证实例上选型，按验证均分选择最终程序，稳健目标只作同分次序；这样最终选型与用户的均分目标保持一致。随后冻结源码。私有 1000 例仅在冻结后评测，不向同一实验的演化反馈。

已知此前 v1/v2 与 kusano 的系统集汇总成绩无法“撤回”，因此整个项目不是从未接触过测试集信息的盲研究；本次限制是 v3 API 搜索不接触私有实例、输出和逐例分数，且选型冻结先于本次私有测试。若测试未达标，必须保留失败结果，不得隐匿后反复宣称一次盲测。

## 完整预算筛选修订

Pro 已保留 15 次请求后，控制器在当前修复及评测完成时安全停止，没有中断在途请求。新增 `--full-evaluation`：短预算仅检查合法性，不再按短预算得分淘汰；所有短预算合法候选均评测 40 个训练实例、每例 4.8 秒。此前因短预算或小样本分数筛掉的合法程序亦补做完整训练评测，原事件不改写，补测单独记入 `evaluation_backfills`。此调整针对 API 生成耗时远高于本地评测的实际成本，避免低保真度排序错过慢启动候选；不增加模型请求上限，不使用验证或私有输入。策略切换记录于 `evaluation_policy_changes`。

当前续跑命令：

```bash
python scripts/v3_search.py --run-dir runs/v3_pro_fromscratch --model deepseek-v4-pro --thinking enabled --effort low --exploration-effort high --max-tokens 65536 --calls 54 --resume --ask-key --full-evaluation --restart-patience 6
```

## 崩溃诊断修订

Pro 20 次请求之后，连续两份同分支候选发生段错误，原反馈只有 RE。安全停在请求边界后，增加独立 ASan/UBSan 与标准库断言构建，对后续 RE 的首个公开反例重放，将诊断位置、标准错误及返回码提供给模型的一次修复。诊断构建仍处于无网络、无旧源码挂载的隔离容器，仅为错误定位，绝不参与性能排名；正式评测仍为原 O3 构建。此次增强没有手改候选源码，也不对过去失败补造成功结果。已通过真实容器的故意越界小程序自测，该自测程序仅用于基础设施验证，不是演化候选。

只读查看进度：`python scripts/v3_status.py`。输出请求状态、已知 token 用量、未知用量请求数和训练成绩；不把未知用量视作零费用。

最终选型开始前先写入 `validation_started`，从此禁止训练演化和训练补测，即使选型被中断或全部候选验证失败，也只能恢复选型，不能回到开发阶段。冻结后的私有评测还会验证与人类基线逐例输入哈希及镜像一致，报告配对胜、平、负；此路径仅在冻结后执行，不为训练加载人类私有结果。

## 停滞重启修订

Pro 21 次请求之后启用 `--restart-patience 6`：自最近一次训练稳健目标提升或独立采样起，连续 6 个完成事件未提升，则用一次现有请求名额进行独立重启。该请求只收到题目和目标，不收到父代代码、已有设计、历史案例或反馈；已有档案完整保留，新程序按相同训练协议竞争。修复优先完成，重启之间至少相隔 6 个事件，避免连续消耗请求。历史策略变更写入 `restart_policy_changes`，独立重启源码也纳入溯源审计。目的在于降低当前表示对后代的锚定，不引入人工解法。

## 档案与推理预算修订

Pro 第 31 次请求（首次独立重启）完成后安全重载。调整前检查发现，15 份合法完整训练程序中，12 份已被其他程序在全部 40 例上不差、且至少一例更好地支配。档案继续保留总体前三及四种规模专家，但算法族额外代表必须处于逐例分数的非支配前沿，避免仅凭模型自报的不同族名称保留全面落后的父代。历史程序不删除。变更写入 `archive_policy_changes`。

同一边界新增 `--exploration-effort high`：独立采样、重启、结构重设计、新设计使用 high 推理，其他算子仍使用 low；总请求上限（Flash 6 + Pro 58）与单次 65536 输出 token 上限不变。实际请求体记录实际强度，已知用量照实累计。该变更不提供人工求解机制。首次重启实测 907.280976M，未替换当时训练最佳 941.189437M；模型假设中的预期得分不是实测结论。

后续记录的 `parents` 仅包含实际提供源码的父代与交叉 donor；此前 `parents` 可能还含一个被选中但未实际传入的 donor。所有时期的准确源码边均以 `source_audit.json` 中 `actual_prompt_source_parents` 为准。

## 公开几何诊断与官方计分复核

进一步加入公开训练布局的阻挡诊断：对两个最低分训练实例中各五个最低满足度矩形，报告目标/实际面积、分数损失贡献、保持其他所有边不动时的四向扩展距离、最近阻挡者及其满足度。这里只测量当前输出，不生成动作、不构造矩形、不搜索解；诊断代码是人工实现的评测基础设施，不声称由 LLM 发明。求解器源码仍全部由 API 响应产生。启用边界记录为 `geometry_feedback_enabled_after_events`。该反馈不读取验证或私有数据。

`python scripts/v3_public_rust_check.py` 可以在开发阶段将当前训练均分最佳的 40 份公开输出交给原始 Rust 计分器复核，不触发冻结或私有评测。已对 Pro call_id 33 的 984.499524M 程序完成 40/40 复核，差异为零；后续程序以各自记录和最终复核为准。

## 机制 donor 修订

Pro 第 41 次请求完成后，交叉 donor 在两种方式间交替：按逐例正向增益选择，或选择最近的合法结构重设计/新设计/独立重启（训练均分落后父代不超过 40M）。后者不必进入主父代档案，从而保留新机制的融合机会，但不让全面落后的程序频繁成为主父代。模型会明确收到 donor 较低的均分、设计说明和选择原因，决定如何融合；控制器不指定几何搜索动作。机制型交叉使用 high 推理，其余普通交叉仍按默认 low。实际来源、选择原因和请求参数均留档，启用事件记录在 `donor_policy_enabled_after_events`。

此修订没有增加请求上限。已通过异步问题询问是否允许在必要时从总计 64 扩至 128 次；在获得明确批准前继续遵守 64 次上限。

## 第二层数值演化

Pro 第 44 次请求完成后，将常规生成阶段上限暂设为 54 次，为模型参数化、参数块安装及修复预留最多四次生成名额；加上 Flash 六次，仍最多 64 次。框架、测试和真实容器参数传递检查已准备完成，实际调优将在常规阶段停止后串行运行。详细机制、预算、来源审计变化和执行命令见 [第二层数值演化](V3_NUMERIC_LAYER.md)。未实际运行的调优不能记作已取得提升。

完整程序与模型生成参数块的审计均使用 `all_sources_match_audited_origin`。参数块安装只允许改变受限的数值默认值区域，其余源码保持父代原文；最终独立程序必须重新评测。

## 运行

```bash
python scripts/v3_search.py --ask-key --calls 64
python scripts/v3_search.py --resume --ask-key --calls 64
# 停止开发、选型并冻结（已用完 64 次则不增加调用）：
python scripts/v3_search.py --resume --ask-key --calls 64 --finalize
```

不带 `--finalize` 的调用预算耗尽后保留开发状态，不读取验证集进行选型，也不自动声称超过目标。运行目录为 `runs/v3_fromscratch`。只能有一个控制进程写入同一目录。
