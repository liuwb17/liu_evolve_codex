# v5.2：ALE-bench 通用演化框架

版本约定：原 GitHub 的 AHC001 专用版称为 v5.0，基础通用版（`052af15`）称为 v5.1，当前版本称为 v5.2。
v5.2 汇总本会话新增的 Plan、随机性声明与三种子评测、四路并行、runtime 干预、父代失败经验、核心预约机制。
包版本为 `0.5.2`，新运行协议和报告版本为字符串 `"5.2"`。
Python 模块/入口仍用 `v5_1_*`，类名仍为 `V51Engine`/`V51Provider`；本文路径也保留，避免无关重命名。
题目数据包格式没有变化，继续使用 `"5.1"`，可复用已有 public 数据包；旧运行需用其原始源码恢复。
下文的 v5.1 表述指沿用的通用实现及文件名，当前发布版本均为 v5.2。

基线：GitHub `liuwb17/liu_evolve_codex` 的 `43a371ad33fe7d6d7244c06c0c83623a3706d8cc`。
历史 v5 的搜索行为保留；其 provider 仅抽取请求体构建方法，以复用原有记账与传输。
v5.1 使用独立入口和协议，没有迁入其他本地版本的代码。

## 已确定的行为

- 支持 ALE-bench `batch` 非交互题，包括 AHC001；拒绝 `reactive` 交互题。
- 控制器为 Python，候选为 C++17。题面、优化方向、时限、内存限制和评分器均来自官方题目包。
- 默认用官方生成器生成 public 种子 0–49，全部用于训练。可配置 public 子集，没有验证集。
- 按官方原始逐例分数的算术平均优化；最大化题保留符号，最小化题内部取负数。
  候选记录保留 `raw_score`、`raw_mean`；`score`、`mean` 是内部有向值，日志里的
  `incumbent_train_mean` 沿用 v5 字段名，表示内部值。最终报告输出原始均分。
- 每个生成/编辑响应必须声明 JSON 布尔值 `is_randomized`。确定性算法评估一次；
  随机算法用固定算法种子 0、1、2 评估三次，按平均分排序和晋升。
  平均提升严格大于 `promotion_margin=0` 即晋升，不再要求至少两次提升。
  `promotion_margin` 单位是原始分数；移除原来的潜力补测、repeat_slack 和 repeat confirmation。
- 冻结时直接固定训练 incumbent，不打开额外数据、不重新选型。
- 独立 `private` 命令在冻结后读取同一官方包的完整 private 实例种子集，运行一次终测流程，
  按算法声明对每个实例运行一次或三个算法种子，输出原始平均分。
  结果不回写搜索状态；冻结后禁止恢复演化。结果是官方种子和工具下的原始均分，
  不计算官方相对排名或 performance。

## 保留与必要变化

默认 `para=None` 保留 v5 的八槽调度、最多 8 个候选/每谱系最多 2 个、强父代优先、互补交叉、
1–6 处协调编辑、整程序重构、失败修复、一次模型调用生成提案、
账本和已完成响应恢复。源码末尾仍使用 `// AAD_V5_COMPLETE`，这是复用的源码合约，
运行协议版本则是字符串 `"5.2"`。

移除 AHC001 几何诊断、`.992` 目标、`1e9` 归一化、固定晋升阈值和 40/10 划分。
反馈保留两个差例的输入、输出、原始分数、错误消息以及耗时。
串行模式的运行时间干预仍以不足半个题目时限触发，不再假设已知满分 `.999`。

官方 ALE 执行器不传 v5 的 `argv[1]`。候选从题面得到固定时限，自行留出退出余量。
因此预检改为前 `smoke_count` 个训练例（默认 6）的**完整官方时限**；不使用 0.6 秒截断。
其后评测剩余训练例，复用预检结果，第一轮不会重跑预检实例。
确定性算法每例总计一次；随机算法再用算法种子 1、2 各完整评估一次。
随机算法不论首轮分数好坏均采用相同评估次数，任意一例非法可提前终止并触发修复。
实例生成种子与算法随机种子是两回事；三次运行不是更多独立测试实例。
编译、资源限制、计时和评分沿用 ALE `run_cases` 的实现，不复用历史 v5 评测缓存。
当前在私有函数副本中适配容器 CPU 绑定及执行前的核心预约，不修改安装的 ALE 文件或全局模块。
不再配置固定 `--workers`；并发由本机核心池决定，详见下节。

ALE 标准 Session 在初始化时会生成 private 输入，因此训练不创建 Session。
准备任务时只提取官方工具及英文题面、public 元数据，调用官方 `generate_inputs`；
终测也直接使用同一生成/评测封装，只有通过冻结门禁才读取 private 种子字段。
不向模型提供 standings、人类源码、private 数据或旧求解器。

## 候选声明和随机种子合约

完整程序响应格式：

```json
{"hypothesis": "本次设计假设", "is_randomized": true, "code": "完整 C++17 源码"}
```

局部编辑保留 `hypothesis`、`parent_sha256`、`edits`，同时必须提供 `is_randomized`。
该声明描述编辑后的完整算法，包含父代继承的随机行为；每次都重新声明，不能默认沿用父代。
缺失或字符串 `"true"`、数字 `1` 等非布尔值会被拒绝。相同源码的矛盾声明也会被拒绝。
使用固定种子的伪随机搜索仍属于随机算法。分类由 LLM 自报，框架不声称已自动证明分类正确。

框架在编译时提供 `AAD_RANDOM_SEED` 宏（0ULL、1ULL、2ULL），模型用它初始化所有 PRNG，
例如 `std::mt19937_64 rng(AAD_RANDOM_SEED);`；禁止重定义该宏或用时钟、random_device 初始化种子。
保存的候选源码保持模型原文；执行时添加固定的宏前缀及 `#line`，缓存记录原始/执行源码哈希。
在框架外单独编译随机程序时，也应通过 `-DAAD_RANDOM_SEED=0` 提供种子。
三个固定种子不保证模型正确使用种子，也不能消除墙钟截止引入的运行波动。

每个个体评测结束后记录 `runtime_ratio`，计算为所有已评测实例/算法种子的平均执行耗时
除以题目时限。预检结果复用，不重复计入；预检失败的个体记录实际已测实例的比值，
但不进入合法档案。`runtime_ratio_basis=total_process_time` 表示使用官方评估器报告的
总执行耗时，不含 LLM、编译、评分或框架调度时间；当前未采集找到最终 incumbent 的时刻。
该比值不截断为 1，并通过父代 timing 反馈提供给 LLM。
`runtime_ratio_protocol=mean-total-process-time-1` 纳入协议指纹。

所有评估保存在候选 `evaluations` 中，`full` 保存聚合分数。均值、候选池和交叉互补比较
都使用同一份聚合分数。反馈示例保留实际某次输出及其实际分数，并另列该实例的平均分，
避免把单次输出错误对应到三次均值。失败反馈优先显示出错的那次评估。
`evaluation_protocol=declared-randomness-1-fixed-seeds` 进入协议指纹；旧检查点使用其固定源码，
不能直接按新评估次数继续。`--repeat-slack` 及旧 `repeats` 配置不再接受。

## 可选 Plan：四个方向引导四个冷启动

`run --plan` 在任何求解器请求之前调用一次同一模型，分析题面与执行约束，返回
`{"directions": ["一句思路", "一句思路", "一句思路", "一句思路"]}`。
每条最多 500 字符、单行且不重复。提示词要求表示、构造或搜索机制有实质区别，
不输出源码、伪代码、诊断器或算法骨架；结构校验不能保证语义上的多样性。
该调用沿用 Solve 的 thinking enabled / low reasoning 设置，使用同一模型，但单独记账。

前四个独立初代尝试依次只收到自己的一条方向，附在原始冷启动指令末尾。
它们不接收其他初代的源码、分数、完整 Plan 或其它三条方向。
仍需从零生成完整 C++17 程序，但初代方向有共同规划来源，不应声称完全无共享先验。
初代失败沿用修复流程，修复后保留方向归属；需要重新冷启动时，在尚无合法谱系的方向中
优先选择尝试次数少者。Plan 模式取消 20 次初代冷启动尝试上限，需要四个方向各形成合法谱系
才进入普通演化；初代不足四个时禁止冻结。演化调用/token 预算仍是停止边界。
失败的初代生成和修复调用仍占用演化预算；串行模式预算耗尽则停止初始化，不额外突破预算。
`para=4` 的末轮补齐规则见下节。串行模式后续八槽调度中的独立重启不附带这些方向；
Plan 不持续指导后续提案、不改变评分或晋升规则。

省略 `--plan` 或显式 `--no-plan` 时不调用规划，维持四个独立冷启动谱系的目标。
如果前四次都成功，则分别是四次初代调用；非法、格式错误或修复会增加实际调用数。

Plan **不计入** `--calls` 和 `--token-budget`。例如 `--calls 128 --plan`
在默认串行模式表示额外一次 Plan，加最多 128 次求解/修复请求。Plan 单次输出上限仍为 65536 tokens。
Plan 请求、响应和费用用量保存于独立 `planning/llm/` 账本，演化请求保存在 `llm/`。
最终报告区分 `plan_requests`、`solve_requests`，`requests` 是二者总和。
四条方向保存在 `plan.json` 和运行状态中，
候选记录/事件中的 `initial_direction` 是从 0 开始的方向索引。
恢复会验证响应哈希和 Plan 产物，复用成功调用；失败、截断或格式不合格则停止，
不会追加 Plan 请求或悄悄转为无 Plan。需要重新尝试时使用新 run。
恢复时必须保持相同的 `--plan`/`--no-plan` 选择及预算；开关和
`plan_protocol=four-cold-start-directions-2-separate-budget` 写入协议指纹。旧提交的运行仍需用其固定源码恢复。

## 可选四路并行：para=4

Python 配置 `para` 仅接受 `None` 或整数 `4`；CLI 省略 `--para` 对应 `None`，
`--para 4` 开启四路并行。它与 `--plan` 独立，可组合使用。

先并行生成四个冷启动初代；Plan 开启时每个初代仅得到对应的一条提示。
失败候选最多修复一次，仍不合法或响应格式失败则重新尝试缺失的初代槽位。
只重试缺失槽位，不增加第五个合法谱系；没有原来的 20 次上限，仍受预算约束。
四个合法谱系齐备后，每轮固定档案快照，并行发出四个 LLM 请求：

| 任务 | 主父代 | 操作 |
|---|---|---|
| 1 | 档案第一名 | local |
| 2 | 档案第一名 | redesign |
| 3 | 档案第一名 | v5 互补收益规则选异谱系 donor；没有逐例正收益时，等概率随机选 redesign/local |
| 4 | 排除第一名谱系，另外三个谱系各取最高分，再等概率抽一个 | 第一轮 redesign，第二轮 crossover，逐轮交替；crossover 的 donor 固定为档案第一名，无互补收益门槛 |

保留档案最多 8 个、每谱系最多 2 个。子代继承主父代的谱系，donor 不改变归属。
每轮若档案第一名的 `runtime_ratio <= 0.30`，任务 4 替换为以**档案第一名为主父代**的
`runtime` 算子，不提供 donor；要求诊断提前结束的原因并增加有助于分数的搜索，禁止空转凑时。
任务 1–3 不变。原 redesign/crossover 交替仍按全局演化轮号推进，被替换的轮次也计入轮号。
并行模式不使用八槽循环、独立重启或停滞改算子；runtime 只由上述 30% 条件触发。
随机选择及四个 prompt 在发送前写入 `parallel_batch`；恢复不重新抽取或选父代。
同轮结果不会进入同轮其它请求的 prompt。LLM 请求并行，候选依次交给评测器，
评测器内部按实例并发执行并独占核心组；本轮评测及一次修复批次处理完毕后再开下一轮。
初代重试和修复批次只调用需要处理的槽位，可能少于四次。

`--calls` 是启动新轮次的边界：剩余调用不足四次时，允许补齐当前轮；
该轮的一次修复批次也允许完成，所有成功、失败、修复和用量未知请求均计入账本。
例如无失败的 `--calls 9 --para 4` 实际调用 12 次（初代 4 + 两轮各 4），
有修复时实际数量还可能增加；不会仅因补齐提高了上限而继续开新轮。
报告分别记录 `requested_calls`、`effective_calls`、实际 `solve_requests`。
Plan 仍独立记账，不占用这些名额。

`--token-budget` 保持硬上限：每批请求发送前一次性检查全部 token 预留，
不够则整批不发送。完整初代已有且待处理批次完全未发送时，可冻结已有 incumbent；
部分已预留的未完成批次或初代不足四个时不能冻结。
账本由主线程统一写入；中断恢复复用已完成响应，已预留但用量未知的请求计作失败，不重发。
`STOP_AFTER_CURRENT` 在批次边界生效；恢复保持原 `--calls`、`--para` 和其它协议参数。
`parallel_protocol=four-lineages-rounds-2-runtime` 记录于协议，新模式应使用新 run 目录。

## 可选父代失败经验

`failure_experience` 默认为 `False`，保留原有行为；`--failure-experience` 开启，
`--no-failure-experience` 显式关闭。适用于串行和 `para=4`，与 Plan 独立。

开启时，每次基于父代的请求要求同一次响应中的 `hypothesis` 用一句话说明：
相对主父代具体改了什么、预期为什么有效。框架评测后，如果子代均分相同或更差，
或编译/运行/输出评测失败，就在这个主父代的 `failure_experience` 中保存一条记录。
记录包含本次 hypothesis、调用编号、算子、子代 ID，以及原始父/子均分和优化方向，
或非法评测状态。严格按主父代的有向均分比较，不受全局 incumbent 或晋升阈值影响。
合法子代修复了非法父代视为成功；两者仍非法则记录失败。

只保留最近 8 条，按处理顺序排列；并行结果按任务顺序处理。
经验绑定具体源码 ID，不传给子代、不共享到同谱系其他个体，交叉 donor 不记该次失败。
每个父代请求的 `parent_failure_experience` 附上这些记录，并提示避免重复失败改动、
考虑其他方法。同轮并行 prompt 使用轮开始时的快照，本轮新失败不会影响同轮请求。
同源码重复提案仍用本次调用的 hypothesis，不误用该源码第一次生成时的描述。

JSON 中有可用 hypothesis 但代码/编辑格式错误时，记录为 `invalid_proposal`，
不伪装成已评测失败；网络错误或完全无法解析的响应没有可用思路，不写算法失败经验，
仍保留原有失败调用账本。该机制不增加 LLM 调用，也不调用 LLM 事后总结。
开关及 `failure_experience_protocol=parent-last-eight-1` 写入协议；恢复必须保持相同配置。

## 本机 9950X3D：按核心资源调度评测

目标机器为 AMD Ryzen 9 9950X3D，16 核 32 线程，Linux Docker Desktop。
运行前通过 Docker 容器读取实际在线 CPU 和 SMT 兄弟线程拓扑；不满足 16 组、每组 2 线程
则拒绝启动，不静默降级为不隔离的评测。当前实际拓扑为 `(0,1)、(2,3)…(30,31)`。

- 前两组（逻辑 CPU 0–3）预留给框架的编译、评分、可视化容器。
- 其余 14 组供求解执行使用。每个“候选 × 实例 × 算法种子”占住整组，
  用 `cpuset_cpus` 绑定到该组的一个逻辑 CPU，兄弟线程不再分给另一个评测。
- 保留 ALE 的一 CPU 配额与原有计时、内存、隔离和评分语义。
- 不设置人工并发上限；实例任务排队，SDK worker 数按可用核心池容量和实例数自动确定。
  单次最多 14 个求解容器；多个本框架进程共享同一 Docker daemon 的预约，合计也最多 14 个。
- Docker 的唯一容器名作为跨进程原子预约。核心占满时每 0.25 秒重试，释放后继续执行。
  先拿到核心再进入官方运行计时函数，排队时间不计入分数或 `runtime_ratio`。
- 退出、编译后运行失败等正常异常路径会清理本任务容器并释放预约。
  进程被强杀、断电或 Docker 失联时可能保留预约；不能确认容器已停止时不抢占该核心。
  此时需先核实无活跃拥有者，再人工清理对应 `aad-v51-core-*` 预约容器。

预约记录保存在各测量目录的 `cpu_leases/`，包含 CPU、兄弟线程、预约 ID、等待秒数和释放状态。
拓扑/分配策略 `9950x3d-smt-leases-1` 进入 runtime 指纹及缓存键，训练和 private 使用相同策略。
旧 `--workers` 参数已移除，旧运行应使用当时固定的源码。

这保证本框架内的评测不共用 Docker 暴露的核心组，不保证 Windows 宿主进程完全不干扰。
本机 WSL/Docker 没有可靠暴露两个 CCD 的缓存分组，不能声称已区分 V-Cache CCD 与频率 CCD，
也不保证各核心性能完全一致；没有修改 Windows 电源策略、系统进程亲和性或 BIOS。

无模型、无候选代码的 Docker 诊断（需要 Docker Python SDK，可用已安装 ALE 的环境）：

```bash
python scripts/v5_1_cpu_check.py --output runs/cpu_check_new
```

2026-10-05 已在本机真实 Docker 验证：占满 14 组时第 15 个任务等待，释放后继续，
容器实际亲和性与分配 CPU 一致；诊断容器已清理。此验证不等同于完整 ALE 题目端到端测试。

## 2026-10-05：容器同步阻塞修复

本机实测发现 ALE 在求解器超时命令之后追加的全局 `sync` 会等待 WSL 内核中的
FUSE 同步请求。求解器已经正常退出，容器仍不结束，导致 14 个核心预约全部占满。
新的 `runtime.execution_protocol=batch-file-fsync-watchdog-1` 将同步范围限制为输出文件和
GNU time 计时文件（`sync -- <output> <profiles>`），保持求解器源码、超时命令、GNU time
计时和官方评分不变。修改只作用于私有 runner 副本，不编辑安装的 ALE SDK。

求解容器等待时间上限为官方 timeout 加 30 秒收尾余量，Docker 常规 RPC 也设置 30 秒上限。
容器等待超时、同步错误作为基础设施异常中止评测，保留 pending 检查点，不转成候选失败分数。
清理无法确认时保留核心预约，不能因超时就把仍可能运行的核心分配给其他任务。
这个 watchdog 限制控制器等待；它不保证能终止已经卡在内核中的容器，后者仍需运维恢复。

套件监控同时检查 state、账本和评测目录的最近活动。超过 20 分钟没有进度显示 `stalled`
并在批次边界停止继续开新请求；等待旧版评测互斥锁时单独显示排队状态。
工作进程失败显示 `needs_attention`，不再只根据进程存活宣称运行正常。

新 execution protocol 进入环境指纹和缓存键。旧实验保持原样；显式恢复可使用
`scripts/v52_migrate_sync.py --source <stopped-suite> --destination <new-suite>`。
迁移仅接受已停止、未冻结的旧运行，核对 SDK、工具、镜像和 CPU 策略未发生其他变化。
已有源码、响应和完成的评测按原来源保留，未完成评测使用修复版重新执行；
`migration.json` 记录原协议、账本哈希以及哪些 smoke/seed/full 结果来自旧协议。
因此这是有记录的恢复实验，不应描述成从头到尾只使用同一执行协议的新实验。

本机验证：AHC001、AHC002、AHC005 各两例官方评测通过；真实 Docker 等待超时故障注入
被归类为基础设施错误，预约正常释放。未调用 LLM，未访问 private。

套件调度脚本 `v52_suite_host.py` / `v52_suite_worker.py` 面向当前 Windows + Ubuntu WSL
环境，使用已有 `schedule.json`、固定源码快照和旧版评测互斥锁；不是通用跨平台启动入口。
常规单题运行继续使用下方的 `v5_1_search.py`。

## 安装与命令

真实评测使用 Linux/WSL、Docker，以及固定的 ALE SDK：

```bash
python -m pip install -e '.[ale-v5-1]'
```

按 [ALE 官方安装说明](https://github.com/SakanaAI/ALE-Bench/tree/3da9b12fb5d112dabb3af693d1a42031c95142bc)
安装系统依赖，并准备 `ale-bench:cpp17-202301` 和 `rust:1.79.0-buster` 镜像。
本机 Windows Python 的离线单元测试不需要 ALE 或 Docker。

```bash
# 默认下载固定数据 revision 0f42617 的题目 ZIP，只生成 public 训练数据。
python scripts/v5_1_search.py prepare --problem ahc001 --output data/v5_1/ahc001

# 换题只改 problem/output；数量例：前 20 个 public 种子。
python scripts/v5_1_search.py prepare --problem ahc002 --output data/v5_1/ahc002 --count 20

# 也可指定 --seeds 0 2 4 6，或 --archive /path/to/official/ahc002.zip。
# prepare 只接受官方 public 种子子集，拒绝用任意种子混入 private。

# 以下 run 会调用付费模型；不是安装验证命令。密钥也可通过 AAD_API_KEY 配置。
python scripts/v5_1_search.py run --task data/v5_1/ahc001 --run-dir runs/v5_1_ahc001 --calls 128 --ask-key

# 可选 Plan；使用新的 run 目录，128 次演化调用，另加一次 Plan。
python scripts/v5_1_search.py run --task data/v5_1/ahc001 --run-dir runs/v5_1_ahc001_plan --calls 128 --plan --ask-key

# 可选四路并行，可与 Plan 组合；末轮和修复可补足调用预算。
python scripts/v5_1_search.py run --task data/v5_1/ahc001 --run-dir runs/v5_1_ahc001_para4 --calls 128 --para 4 --plan --ask-key

# 可选父代失败经验，同样使用独立的新运行目录。
python scripts/v5_1_search.py run --task data/v5_1/ahc001 --run-dir runs/v5_1_ahc001_memory --calls 128 --para 4 --failure-experience --ask-key

# 如需恢复，保持相同参数并增加 --resume；STOP_AFTER_CURRENT 保留 v5 语义。
# 完成训练后明确冻结，再终测。freeze 不调用模型或评测器。
python scripts/v5_1_search.py freeze --task data/v5_1/ahc001 --run-dir runs/v5_1_ahc001
python scripts/v5_1_search.py private --task data/v5_1/ahc001 --run-dir runs/v5_1_ahc001
```

若准备时指定了自备官方 ZIP，终测用 `--archive` 指向相同文件；SHA256 必须相同。
准备目录和新运行目录必须为空。每个 run 有排他锁；异常断电残留锁需确认没有进程再人工处理。
private 命令开始前写排他 receipt；失败也保留，不自动重试或重复查看私有结果。

运行记录包含任务包/输入/实现哈希、SDK 源码哈希、官方工具二进制哈希、Docker 镜像 ID，
配置变化或源码变化会拒绝恢复。开发环境更新后应新建 run；不能修改冻结运行再声称原协议。
