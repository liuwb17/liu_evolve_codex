# MOSAIC v2：970M 目标对应的改进

本版保留 v1 实验和源码，另开 `runs/v2_deepseek`。v1 的官方 1000 例成绩是 903.07M，不修改其历史记录。

## 主要瓶颈与改进

v1 只有少量模型试验，候选语言为 Python，搜索邻域以单矩形修改为主。邻居挡住扩张时，单独修改该矩形常常无法取得正向增益。模型产物还使用了不准确的内部面积近似目标。

v2 引入 C++17 和一个明确标记为人工工程基线的联合邻域骨架：提出矩形扩张、平移、形状变化或收缩，检测与其冲突的邻居，并同时裁剪这些邻居。所有矩形继续包含其指定点；邻居只缩小，因此不会引入新的邻居间重叠。使用真实满意度之和计算联合变化，允许退火接受暂时损失，以重新分配局部空间。

固定骨架中的 `quality()` 使用原题 min/max 面积公式。它不是候选程序自报成绩：所有输出仍由独立 Python checker 评测，终局由原始 Rust 工具复核。算法内部准则正确也不能替代输出合法性检查。

## 更细的演化边界

`parameters`：步长、温度和移动分布参数。

`proposal`：几何提案，例如扩张、平移、面积保持的形状调整。

`conflict`：冲突邻居的可行裁剪与空间交换。

`schedule`：温度日程。

`search`：完整搜索循环，可作结构重写或组合。

模型返回修改假设和完整源码块。只允许替换已有块，C++ 编译在隔离容器内进行，编译错误反馈用于最多一次局部修复。候选缓存同时包含源码、输入、镜像与搜索时长，防止跨预算混用分数。

## 搜索与选择协议

控制器维护最多 8 个进入父代选择的高分候选，65% 选择当前训练最佳，其余从保留候选中随机选择。不同算子轮换；另一候选作为跨程序启发。所有请求、源代码、父代、失败诊断和评测结果存档。

开发集是新生成样例：训练种子 40000–40015，验证种子 60000–60023；这些使用题面分布和 Python RNG，不是官方系统种子。候选先在同一组 4 例、0.5 秒预算下筛选，再在完整 16 例、0.5 秒预算下比较。保留的前 3 个候选使用 24 例、4.25 秒预算选择最终程序。随后冻结源码，在新生成的 80 例留出样例（80000–80079）上测试。最后才评测官方 1000 个系统种子。

控制器按相同预算排序；开发短跑不能直接与完整预算成绩混报。执行硬上限为 5 秒，候选容器限制 1 CPU、512 MiB，禁网、只读挂载、非 root。终局采用 4.25 秒搜索预算，保留容器启动与结束余量。

## 运行方法

```bash
docker build -f docker/Dockerfile.cpp -t mosaic-cpp:1 docker
python scripts/v2_search.py --run-dir runs/v2_new --ask-key --calls 12
# 中断后继续，保留已用请求计数：
python scripts/v2_search.py --run-dir runs/v2_new --ask-key --calls 12 --resume
# 只对已冻结候选作官方 1000 例终局测试：
python scripts/v2_system_test.py
```

密钥只通过隐藏输入或 `AAD_API_KEY` 使用。初始思考模式曾耗尽输出预算而未返回代码；后续改为直接代码生成。一次被中断的请求无法取得完整 token 使用，账本标为 `interrupted_usage_unknown`，不将其假定为免费，也不伪造 token 数。

## 如何理解改进来源

新邻域骨架和 C++ 后端是本次人工工程投入，不能算作模型从零发现。模型在该骨架上演化源码块；是否带来额外改进应查看等预算基线与模型候选的记录。最终候选来源记录为 `human-engineered-seed` 或 `deepseek`。语言、初始算法与模型配置同时变化，因此不能仅凭新旧最终分数证明某个框架组件单独造成提升。

阶段数据：人工新基线 16 例/0.5 秒均分 972.78M；人工新基线 24 例/4.25 秒均分 985.57M。最终模型和官方结果以各运行目录中的实际报告为准。

## 终局运行预算调整

冻结程序在 24 例选型验证集上为 987.927538M，在 80 例独立合成留出集上为 986.692411M，均采用 4.25 秒搜索预算。验证集上对人工骨架的同预算增益为 2.361789M；没有运行多随机种子的消融实验，不能作统计显著性或框架优势推断。

2026-09-19 的首次官方终局尝试采用 4.25 秒、并发 6，观察到超时后中断；96 条已完成缓存记录中有 90 AC / 6 TLE，均分 924.289021M（失败计零），不是完整 1000 例结果。完整原始记录保存在 `runs/v2_system_1000/interrupted.json`，未删除失败记录。

随后保持同一源码哈希，将统一搜索预算降为 3.5 秒，仍以 5 秒为含容器启动的硬上限、并发 6，使用独立缓存从头重测。该轮仍出现超时，在 246 条已完成记录中有 231 AC / 15 TLE，均分 925.130045M（失败计零），原始记录保存在 `runs/v2_system_1000_final/interrupted.json`。部分超时已收到程序输出，说明容器生命周期计时混入了程序之外的开销；不能仅据此断言每次失败都是 Docker 而非程序导致。

最终运行采用独立的容器内受信计时器：候选进程从启动到输出结束限时 5 秒，包含进程 I/O；容器外基础设施单独设 30 秒上限并记录总耗时。程序仍使用 3.5 秒搜索预算、1 CPU/512 MiB、并发 6。再次使用全新缓存重测全部 1000 例，结果目录为 `runs/v2_system_1000_runtime5/`。容器内与外部计时分别保存为 `seconds` 和 `container_wall_seconds`。

这是观察到系统集运行问题后的预算与计时口径调整，不能宣称最终协议是在接触系统集前预注册的，也不能说最终结果满足旧的“含 Docker 启停 5 秒”限制。未按系统集分数演化源码，也未只重试失败样例；不提供官方标准硬件排名。

`python scripts/v2_system_test.py` 默认采用上述最终配置。C++ 文件本身仍保留冻结时的 4.25 秒默认值；复现终局运行必须显式传入参数 `3.5`，例如 `./solution 3.5 < input.txt > output.txt`。工具不会修改交付的冻结源码。
